# STO Report Generator

Генератор собирает русскоязычные учебные, курсовые, НИР и ВКР-отчеты в `.docx` из модульных Markdown-файлов. После Word-постобработки рядом с DOCX автоматически создается PDF для быстрой проверки верстки. Сборка ориентирована на СТО Самарского университета: титульный лист, оглавление, основной шрифт Times New Roman 14 pt, абзацный отступ 1,25 см, полуторный интервал, подписи таблиц и рисунков, библиография и проверки итогового DOCX.

## Что умеет генератор

\begin{sto_list}
- собирает отчет из нескольких `.md` файлов, отсортированных по имени;
- формирует титульный лист по YAML-блоку в `00_metadata.md`;
- вставляет структурные заголовки `РЕФЕРАТ`, `СОДЕРЖАНИЕ`, `ЗАКЛЮЧЕНИЕ`, `СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ`;
- преобразует inline- и block-формулы LaTeX в Word OMML;
- нумерует формулы по правому краю через метки `@eq:*`;
- форматирует таблицы, рисунки, перечни и библиографию;
- выполняет Word-постобработку: обновляет оглавление, считает страницы/рисунки/таблицы/источники, повторяет заголовки таблиц, центрирует и масштабирует рисунки, исправляет Word-формулы;
- экспортирует PDF рядом с финальным DOCX;
- проверяет исходный Markdown и распакованный DOCX валидаторами.
\end{sto_list}

## Установка

Нужны Node.js, npm, Python-раннер `uv` и установленный Microsoft Word для `scripts/post_build.py`.

```powershell
npm install
```

## Структура отчета

Папка отчета должна лежать, например, в `reports/my_report`. Генератор читает все `.md` файлы из папки и склеивает их в алфавитном порядке. Поэтому файлы нумеруются префиксами:

```text
00_metadata.md
01_referat.md
02_toc.md
03_intro.md
10_methodology.md
20_data.md
30_results.md
90_conclusion.md
91_sources.md
references.bib
images/
```

`00_metadata.md` содержит YAML frontmatter. `02_toc.md` обычно содержит только:

```tex
\sto_structural_heading{СОДЕРЖАНИЕ}
```

`91_sources.md` должен содержать bibliography-окружение:

```tex
\sto_structural_heading{СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ}

\begin{sto_bibliography}
\end{sto_bibliography}
```

## Сборка

Рекомендуемый порядок для любого отчета:

```powershell
npx tsx tests/regression_checks.ts reports/my_report
npx tsx src/index.ts reports/my_report reports/my_report/my_report.docx
uv run --with pywin32 --with lxml python scripts/post_build.py reports/my_report/my_report.docx reports/my_report
npm run unpack -- reports/my_report/my_report.docx .temp_my_report_docx
npm run validate:sto -- .temp_my_report_docx
```

Для встроенного примера:

```powershell
npx tsx tests/regression_checks.ts example
npx tsx src/index.ts example example/output.docx
uv run --with pywin32 --with lxml python scripts/post_build.py example/output.docx example
npm run unpack -- example/output.docx .temp_example_docx
npm run validate:sto -- .temp_example_docx
```

Важно: `post_build.py` лучше запускать с двумя аргументами: путь к DOCX и путь к исходной папке Markdown. Второй аргумент нужен для восстановления корректных Word-формул из исходного LaTeX. После этого рядом с DOCX будет создан PDF с тем же именем файла. Если нужен другой путь PDF, передайте его третьим аргументом:

```powershell
uv run --with pywin32 --with lxml python scripts/post_build.py reports/my_report/my_report.docx reports/my_report reports/my_report/my_report_preview.pdf
```

## Абзацы и текст

Обычный текст пишется обычными абзацами Markdown. Генератор применяет стиль `Normal`: Times New Roman 14 pt, полуторный интервал, выравнивание по ширине и красную строку 1,25 см.

После блочной формулы абзац, начинающийся со слова `где`, автоматически идет без красной строки. Точку в конце формулы перед таким абзацем ставить нельзя.

Правильно:

```markdown
$$y_i = \frac{O_i}{D_i},$$

где $y_i$ – доля просроченной задолженности, $O_i$ – просроченная задолженность, $D_i$ – совокупная задолженность.
```

Неправильно:

```markdown
$$y_i = \frac{O_i}{D_i}.$$

где ...
```

## Перечни

В отчетных `.md` файлах не используйте сырые Markdown-списки. Для перечней обязательно оборачивайте элементы в STO-окружения.

Маркированный перечень:

```tex
\begin{sto_list}
- первый элемент;
- второй элемент;
- третий элемент.
\end{sto_list}
```

Нумерованный перечень:

```tex
\begin{sto_enum}
1. первый этап;
2. второй этап;
3. третий этап.
\end{sto_enum}
```

Сырые списки вне этих окружений валидатор считает ошибкой:

```markdown
- так писать в отчете нельзя;
- используйте sto_list.
```

## Формулы

Inline-формулы пишутся через одинарные `$...$`:

```markdown
Целевая переменная $y_i$ ограничена диапазоном от 0 до 1.
```

Блочные формулы пишутся через `$$...$$`:

```markdown
$$\bar{y} = \frac{1}{n}\sum_{i=1}^{n} y_i,$$
```

Если формула должна иметь номер, добавьте автоматическую метку в конце формулы:

```markdown
Функция плотности нормального распределения задается формулой @eq:normal_dist:

$$f(x) = \frac{1}{\sigma\sqrt{2\pi}}\exp\left(-\frac{(x-\mu)^2}{2\sigma^2}\right) (@eq:normal_dist)$$
```

В DOCX такая формула будет центрирована, а номер будет выведен справа как `(1)`. Ссылка `@eq:normal_dist` в тексте заменится на номер формулы. Не ставьте номера вручную:

```markdown
$$f(x)=... (1)$$
```

Такой вариант запрещен, потому что при перестановке формул номера станут неверными.

## Таблицы

Перед таблицей в тексте должна быть ссылка на нее: «... приведены в таблице 1». Затем идет подпись и сама Markdown-таблица.

```markdown
Основные характеристики приведены в таблице 1.

Таблица 1 – Основные характеристики панели (@tab:panel_summary)
| Показатель | Значение |
|---|---:|
| Число территорий | 83 |
| Число признаков | 33 |
```

Текст после таблицы оформляется обычным абзацем с красной строкой. `post_build.py` добавляет небольшой интервал после обычных таблиц и переносит небольшие таблицы целиком, если они разрываются внизу страницы.

## Рисунки

Перед рисунком в тексте должна быть ссылка на него: «... показано на рисунке 1». Затем идет изображение и подпись.

```markdown
Распределение целевой переменной показано на рисунке 1.

![Распределение доли просрочки](reports/my_report/images/target_distribution.png)

Рисунок 1 – Распределение доли просрочки демонстрирует правый хвост (@fig:target_distribution)
```

Путь к рисунку задается относительно корня репозитория. Для финального DOCX используйте PNG или JPEG. SVG допустим в примере, но для отчетов с научными графиками надежнее PNG.

## Библиография

Источники хранятся в `references.bib`. В тексте используйте cite-ссылки:

```markdown
Непараметрический подход устойчивее к выбросам [@kruskal1952].
```

Список литературы формируется автоматически из реально процитированных ключей в порядке первого появления.

## Что проверяют валидаторы

`tests/regression_checks.ts` проверяет исходный Markdown:

\begin{sto_list}
- нет битых ссылок `NOT FOUND`;
- нет длинного тире `—` вместо среднего тире `–`;
- нет цитаты `[0]`;
- нет жирного Markdown вне `01_referat.md`;
- все локальные изображения существуют;
- таблицы и рисунки упомянуты до появления;
- нет сырых Markdown-перечней вне `sto_list` и `sto_enum`;
- нет ручной нумерации формул вида `(1)`;
- нет дублирующихся меток `@eq:*`.
\end{sto_list}

`validate:sto` проверяет распакованный DOCX:

\begin{sto_list}
- стили заголовков, обычного текста, таблиц и рисунков;
- отсутствие непересчитанных полей Word;
- корректность формул и знаков умножения;
- отсутствие точки в формуле перед абзацем `где`;
- повтор заголовков таблиц;
- ширину и центрирование рисунков;
- оформление библиографии и перечней.
\end{sto_list}

## Частые ошибки

\begin{sto_list}
- Не запускается `post_build.py`: проверьте, что Microsoft Word установлен и DOCX не открыт вручную.
- PDF не обновляется: закройте PDF в просмотрщике, если он блокирует перезапись файла.
- В формуле плохо отображается сумма, черта или тильда: запускайте `post_build.py` с исходной папкой отчета вторым аргументом.
- Валидатор ругается на список: оберните список в `\begin{sto_list}` или `\begin{sto_enum}`.
- Валидатор ругается на номер формулы: уберите ручной номер и используйте `(@eq:formula_id)`.
- Рисунок не найден: проверьте путь от корня репозитория, например `reports/my_report/images/figure.png`.
\end{sto_list}
