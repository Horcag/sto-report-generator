# STO Report Generator

Генератор собирает русскоязычные учебные, курсовые, НИР и ВКР-отчеты в `.docx` из модульных Markdown-файлов. После
Word-постобработки рядом с DOCX автоматически создается PDF для быстрой проверки верстки. Сборка ориентирована на СТО
Самарского университета: титульный лист, оглавление, основной шрифт Times New Roman 14 pt, абзацный отступ 1,25 см,
полуторный интервал, подписи таблиц и рисунков, библиография и проверки итогового DOCX.

## Что умеет генератор

\begin{sto_list}

- собирает отчет из нескольких `.md` файлов, отсортированных по имени;
- формирует титульный лист по YAML-блоку в `00_metadata.md`;
- вставляет структурные заголовки `РЕФЕРАТ`, `СОДЕРЖАНИЕ`, `ЗАКЛЮЧЕНИЕ`, `СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ`;
- преобразует inline- и block-формулы LaTeX в Word OMML;
- нумерует формулы по правому краю через метки `@eq:*`;
- форматирует таблицы, рисунки, перечни и библиографию;
- выполняет Word-постобработку: обновляет оглавление, считает страницы/рисунки/таблицы/источники, повторяет заголовки
  таблиц, центрирует и масштабирует рисунки, исправляет Word-формулы;
- экспортирует PDF рядом с финальным DOCX;
- проверяет исходный Markdown и распакованный DOCX валидаторами.
  \end{sto_list}

Важно: `\begin{sto_list}`, `\begin{sto_enum}` и `\begin{sto_bibliography}` - это не обычный Markdown и не полноценный
LaTeX. Это собственные STO-макросы генератора. Они поддерживаются парсером, но теперь парсер и preflight-валидатор
отклоняют неизвестные `\begin{...}` и несовпадающие `\end{...}`.

## Установка

Нужны Node.js, npm, Python-раннер `uv` и установленный Microsoft Word для Word COM/PDF-шагов `scripts/post_build.py`. Формулы конвертируются через npm-пакет `@hungknguyen/mathml2omml`, без системного `MML2OMML.XSL`. Внутренняя архитектура Python post-build описана в `docs/architecture/python-post-build.md`.

```powershell
npm install
uv sync
npm run hooks:install
```

`uv sync` создает изолированное Python-окружение `.venv` для Python-части генератора. Хуки ставятся через `pre-commit`;
в `.pre-commit-config.yaml` включены `pre-commit` и `pre-push` стадии.

Если нужны Python-зависимости для построения графиков, установите дополнительную группу:

```powershell
uv sync --group figures
```

## Архитектура и правила

Основная архитектура остается TypeScript + FSD-подобные слои:

\begin{sto_list}

- `src/app` - сборка отчета и orchestration;
- `src/features` - Markdown-парсер, формулы, таблицы, изображения, STO-макросы;
- `src/entities` - доменные типы отчета;
- `src/widgets` - крупные DOCX-блоки вроде титульного листа;
- `src/shared` - общие конфиги, стили и XML-валидаторы.
  \end{sto_list}

Архитектуру проверяет пакет `steiger`:

```powershell
npm run fsd:check
```

Базовые STO-константы вынесены в `src/shared/config/sto-rules.json`: поддерживаемые STO-окружения, типографика, поля
страницы, базовые правила валидаторов. Не храните там локальные абсолютные пути; конфиг должен оставаться переносимым.
Покрытие перенесенных и оставшихся правил СТО ведется в `docs/sto-rules-coverage.md`.
Параметры, перенесенные из `.dotm`-шаблона, зафиксированы в `docs/architecture/dotm-template-style-audit.md`.
Короткий пользовательский гайд по написанию Markdown-отчетов находится в `docs/report-authoring.md`.

## Структура отчета

Папка отчета должна лежать, например, в `reports/my_report`. Генератор читает все `.md` файлы из папки и склеивает их в
алфавитном порядке. Поэтому файлы нумеруются префиксами:

```text
00_metadata.md
01_referat.md
02_toc.md
03_intro.md
10_methodology.md
20_data.md
30_results.md
90_conclusion.md
91_sources.md
references.bib
images/
```

`00_metadata.md` содержит YAML frontmatter. `02_toc.md` обычно содержит только:

```tex
\sto_structural_heading{СОДЕРЖАНИЕ}
```

`91_sources.md` должен содержать только заголовок списка источников и пустое bibliography-окружение:

```tex
\sto_structural_heading{СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ}

\begin{sto_bibliography}
\end{sto_bibliography}
```

Внутрь `sto_bibliography` не нужно переносить вручную весь список литературы. Генератор сам подставляет туда только те записи из `references.bib`, которые реально процитированы в тексте через `[@key]`. Поэтому `references.bib` может быть большой общей библиотекой, а итоговый список использованных источников останется коротким и синхронным с текстом.

## Создание и сборка

Создать новую папку отчета с шаблонами, `report.config.json`, локальным `.gitignore` и вложенным `git init`:

```powershell
npm run new:report -- my_report --profile coursework --dir reports/my_report --title "Название темы"
```

Если вложенный git не нужен:

```powershell
npm run new:report -- my_report --dir reports/my_report --no-git
```

Поддерживаемые профили:

\begin{sto_list}

- `nir` - полный НИР-шаблон: реферат, содержание, введение, основная часть, заключение, источники;
- `coursework` - полный шаблон курсовой работы с теми же обязательными структурными элементами;
- `lab` - облегченный шаблон лабораторной работы: без реферата, содержания и источников по умолчанию.
  \end{sto_list}

`--type` задает только строку на титульном листе и не заменяет `--profile`. Для титульника можно также передать
`--department`, `--subdepartment`, `--specialty-code`, `--specialty-name`, `--profile-name`, `--semester`, `--year`,
`--student`, `--group`, `--supervisor`, `--hide-signatures`.

Рекомендуемый цикл для любого отчета:

```powershell
npm run check:source -- reports/my_report
npm run generate:report -- reports/my_report --post-build --validate
```

Полный аудит тем же pipeline через одну команду:

```powershell
npm run audit:report -- reports/my_report
```

`check:source` по умолчанию падает только на ошибках. Эвристические СТО-замечания выводятся как `WARN`. Для финальной
вычитки перед сдачей можно включить строгий режим, где warnings тоже считаются нарушениями:

```powershell
npm run check:source -- reports/my_report --strict
```

`generate` и `check:source` читают `report.config.json`. По умолчанию scaffold задает переносимые относительные пути:
`sourceDir: "."`, `outputDocx: "build/<slug>.docx"`, `validate.unpackDir: ".temp_docx"`. Не добавляйте в общий
репозиторий абсолютные локальные пути вроде `D:/...` или `C:/Users/...`; preflight считает такие пути ошибкой
конфигурации.

Минимальная схема профильного конфига:

```json
{
	"profile": "lab",
	"sourceDir": ".",
	"outputDocx": "build/lab.docx",
	"document": {
		"requiredStructuralHeadings": ["ВВЕДЕНИЕ", "ЗАКЛЮЧЕНИЕ"],
		"optionalStructuralHeadings": [
			"СОДЕРЖАНИЕ",
			"СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ"
		],
		"requireReferat": false,
		"requireSources": "when-cited"
	},
	"preflight": {
		"strict": false,
		"softTextRules": "warning"
	}
}
```

`requireSources: "when-cited"` означает, что `СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ`, `references.bib` и
`sto_bibliography` становятся обязательными только после появления cite-ссылок `[@key]`.

Раздельные команды остаются доступны, если нужно отладить конкретный шаг:

```powershell
npx tsx src/index.ts build reports/my_report reports/my_report/build/my_report.docx
uv run python scripts/post_build.py reports/my_report/build/my_report.docx reports/my_report
npm run validate:docx -- reports/my_report/build/my_report.docx .agent-work/my_report_unpacked
```

Для встроенного примера:

```powershell
npm run check:source -- example
npx tsx src/index.ts build example example/output.docx
uv run python scripts/post_build.py example/output.docx example
npm run validate:docx -- example/output.docx .agent-work/example_unpacked
```

Важно: `post_build.py` остается совместимой точкой входа, но реализация живет в `scripts/sto_post_build/`. Лучше запускать его с двумя аргументами: путь к DOCX и путь к исходной папке Markdown. Второй аргумент нужен для восстановления корректных Word-формул из исходного LaTeX. После этого рядом с DOCX будет создан PDF с тем же именем файла. Если нужен другой путь PDF, передайте его третьим аргументом:

```powershell
uv run python scripts/post_build.py reports/my_report/build/my_report.docx reports/my_report reports/my_report/build/my_report_preview.pdf
```

Полный quality gate без Word-постобработки:

```powershell
npm run quality
```

CI запускает тот же non-Word gate (`format:check`, ESLint с `--max-warnings=0`, TypeScript, Steiger, тесты), Python
quality через `uv sync --group dev`, `ruff` и `mypy`, а также optional Sonar scan при наличии `SONAR_TOKEN`. Release
workflow собирает npm tarball для тегов `v*` и ручного запуска.

## Абзацы и текст

Обычный текст пишется обычными абзацами Markdown. Генератор применяет стиль `Normal`: Times New Roman 14 pt, полуторный
интервал, выравнивание по ширине и красную строку 1,25 см.

После блочной формулы абзац, начинающийся со слова `где`, автоматически идет без красной строки. Точку в конце формулы
перед таким абзацем ставить нельзя. Двоеточие после `где` тоже запрещено.

Правильно:

```text
$$y_i = \frac{O_i}{D_i},$$

где $y_i$ – доля просроченной задолженности, $O_i$ – просроченная задолженность, $D_i$ – совокупная задолженность.
```

Неправильно:

```text
$$y_i = \frac{O_i}{D_i}.$$

где: ...
```

## Перечни

В отчетных `.md` файлах не используйте сырые Markdown-списки. Для перечней обязательно оборачивайте элементы в
STO-окружения.

Маркированный перечень:

```tex
\begin{sto_list}
- первый элемент;
- второй элемент;
- третий элемент.
\end{sto_list}
```

Нумерованный перечень:

```tex
\begin{sto_enum}
1. первый этап;
2. второй этап;
3. третий этап.
\end{sto_enum}
```

Сырые списки вне этих окружений валидатор считает ошибкой:

```markdown
- так писать в отчете нельзя;
- используйте sto_list.
```

## Формулы

Inline-формулы пишутся через одинарные `$...$`:

```markdown
Целевая переменная $y_i$ ограничена диапазоном от 0 до 1.
```

Блочные формулы пишутся через `$$...$$`:

```markdown
$$\bar{y} = \frac{1}{n}\sum_{i=1}^{n} y_i,$$
```

Если формула должна иметь номер, добавьте автоматическую метку в конце формулы:

```markdown
Функция плотности нормального распределения задается формулой @eq:normal_dist:

$$f(x) = \frac{1}{\sigma\sqrt{2\pi}}\exp\left(-\frac{(x-\mu)^2}{2\sigma^2}\right) (@eq:normal_dist)$$
```

В DOCX такая формула будет центрирована, а номер будет выведен справа как `(1)`. Ссылка `@eq:normal_dist` в тексте
заменится на номер формулы. Не ставьте номера вручную:

```markdown
$$f(x)=... (1)$$
```

Такой вариант запрещен, потому что при перестановке формул номера станут неверными.

## Таблицы

Перед таблицей в тексте должна быть ссылка на нее: «... приведены в таблице 1». Затем идет подпись и сама
Markdown-таблица.

```markdown
Основные характеристики приведены в таблице 1.

Таблица 1 – Основные характеристики панели (@tab:panel_summary)
| Показатель | Значение |
|---|---:|
| Число территорий | 83 |
| Число признаков | 33 |
```

Текст после таблицы оформляется обычным абзацем с красной строкой. `post_build.py` добавляет небольшой интервал после
обычных таблиц и переносит небольшие таблицы целиком, если они разрываются внизу страницы.

## Рисунки

Перед рисунком в тексте должна быть ссылка на него: «... показано на рисунке 1». Затем идет изображение и подпись.

```text
Распределение целевой переменной показано на рисунке 1.

![Распределение доли просрочки](images/target_distribution.png)

Рисунок 1 – Распределение доли просрочки демонстрирует правый хвост (@fig:target_distribution)
```

Путь к рисунку задается относительно папки отчета; fallback относительно корня репозитория сохранен для старых отчетов.
Для финального DOCX используйте PNG или JPEG. SVG допустим в примере, но для отчетов с научными графиками надежнее PNG.

## Библиография

Источники хранятся в `references.bib`. В тексте используйте cite-ссылки по BibTeX-ключам:

```markdown
Непараметрический подход устойчивее к выбросам [@kruskal1952].
Несколько источников указываются в одной ссылке [@kruskal1952; @mann1947].
```

Поддерживаются разделители `;` и `,` внутри одной cite-ссылки. При сборке первая встреченная запись получает номер `[1]`, следующая новая запись - `[2]` и так далее. Повтор той же записи получает уже выданный номер.

Правила, которые нельзя нарушать:

\begin{sto_list}

- не пишите вручную `[1]`, `[2]` и другие номера источников в исходном Markdown;
- не оставляйте в тексте ключи, которых нет в `references.bib`, иначе сборка должна упасть;
- не вставляйте ручной список литературы внутрь `91_sources.md`, если используете `references.bib`;
- не используйте `[0]`, нумерация источников начинается с `[1]`.
  \end{sto_list}

Список литературы формируется автоматически из реально процитированных ключей в порядке первого появления. Валидатор DOCX проверяет, что после сборки не осталось `[@key]`, а номера использованных источников идут плотно от `[1]` до `[N]` без пропусков.

## Что проверяют валидаторы

`tests/source-preflight/regression_checks.ts` проверяет исходный Markdown:

\begin{sto_list}

- нет битых ссылок `NOT FOUND`;
- нет длинного тире `—` вместо среднего тире `–`;
- нет цитаты `[0]`;
- нет ручных номеров источников `[1]`, `[1, 2]` в исходном Markdown;
- нет табов;
- нет `где:` после формул;
- нет жирного Markdown вне `01_referat.md`;
- все локальные изображения существуют;
- таблицы и рисунки упомянуты до появления;
- подписи таблиц и рисунков не заканчиваются точкой;
- заголовки markdown-таблиц не пустые и не заканчиваются точкой;
- markdown-таблицы не содержат пустых ячеек;
- нет сырых Markdown-перечней вне `sto_list` и `sto_enum`;
- нет запрещенных буквенных маркеров перечней (`ё`, `з`, `й`, `о`, `ч`, `ъ`, `ы`, `ь`) и маркеров вида `1).`;
- нет неизвестных или несбалансированных `\begin{...}` окружений;
- нет ручной нумерации формул вида `(1)`;
- нет `*`/`·`, `:` как знака деления и десятичной точки внутри блочных формул;
- нумерованные формулы с `@eq:*` действительно используются в тексте;
- формулы подряд без текста разделены запятой или точкой с запятой;
- обязательные структурные элементы идут в порядке СТО;
- приложения стоят после источников, имеют неповторяющиеся буквенные обозначения и ссылки до заголовка приложения;
- реферат содержит плейсхолдеры статистики `{{PAGES}}`, `{{FIGURES}}`, `{{TABLES}}`, `{{SOURCES}}`;
- нет дублирующихся меток `@eq:*`.
- `report.config.json` не содержит неизвестный профиль, неизвестные структурные заголовки, абсолютные локальные пути и
  некорректные enum-значения;
- profile/config определяет обязательные структурные элементы, реферат и необходимость списка источников;
- metadata/frontmatter содержит поля титульного листа с корректными типами `semester` и `year`;
- metadata/frontmatter соответствует выбранному профилю `nir`, `coursework` или `lab`, а `specialtyCode` выглядит как
  `01.03.02`;
- cite-ссылки имеют соответствующие BibTeX-записи до этапа сборки;
- процитированные электронные источники с `url` содержат дату обращения `urldate`;
- `sto_bibliography` остается пустым контейнером, без ручного списка литературы;
- markdown-заголовки не пустые, не заканчиваются точкой и не перескакивают уровни.
  \end{sto_list}

Предупреждения (`WARN`) показывают стилистические или эвристические нарушения: прямые кавычки в тексте, десятичную точку
в обычном тексте, пунктуацию элементов перечня, точку в конце строки ключевых слов реферата, отсутствие ожидаемых
смысловых маркеров реферата, подозрительные сокращения, цифры 1-9 в простом тексте, `D` как знак диаметра и ошибки
оформления примечаний. В `--strict` режиме эти предупреждения также делают проверку неуспешной.

`validate:sto` проверяет распакованный DOCX:

\begin{sto_list}

- стили заголовков, обычного текста, подписей и текста таблиц;
- поля всех секций, базовый шрифт и кегль;
- отсутствие dirty-флагов полей Word;
- наличие номера страницы в нижнем колонтитуле по центру и отсутствие видимого номера на титульном листе;
- корректность формул и знаков умножения;
- отсутствие незамененных cite-ссылок `[@key]`;
- плотную нумерацию использованных источников от `[1]` до `[N]`;
- отсутствие точки в формуле перед абзацем `где`;
- отсутствие табов и пустых ячеек таблиц;
- отсутствие точки в заголовках таблиц на уровне DOCX XML;
- соседство подписи таблицы с таблицей и рисунка с подписью;
- отсутствие диагональных границ в таблицах;
- повтор заголовков таблиц;
- ширину и центрирование рисунков;
- оформление библиографии и перечней.
  \end{sto_list}

## Частые ошибки

\begin{sto_list}

- Не запускается `post_build.py`: проверьте, что Microsoft Word установлен и DOCX не открыт вручную.
