# Wordcraft 0.9.0: Word and platform comparison

## Runtime

The opt-in renderer now requires CLI **0.9.0**, release commit
`2e6db0bd88795e80375176c01665cff7dbe2b057`.
The [user compatibility matrix](../wordcraft-compatibility.md) explains the practical limits in Russian.
The portable default and separate Word acceptance remain unchanged.

## Method and limits

Each case starts with one frozen source DOCX. Wordcraft uses the production staging, statistics,
field-update and convergence workflow. Word uses `npm run accept:word -- <docx>`:
Microsoft Word 16.0, build 16.0.20430, current default printer OneNote (Desktop), fields/TOC update,
table fitting/splitting, referat statistics, saved-document reopen and PDF export.
These are comparisons of the supported workflows, not isolated layout algorithms: our Word path
also performs table repairs absent from the Wordcraft path.

Font controls use the same Windows font files for Times New Roman regular/bold/italic/bold-italic,
Cambria Math/Cambria, Arial, Calibri and Courier New. A temporary CLI-only HOME exposes these
files through its font directory; no global font installation or user configuration change is made.
`font.list` confirms discovery; PDF font resources confirm use. Default WSL runs without that
directory resolve to Liberation Serif/Mono and DejaVu Math TeX Gyre. System `fc-match` alone does
not describe Wordcraft's direct font discovery.

Independent inspection uses pypdf 6.10.0, PDFium and Pillow from the bundled document runtime.
The new `scripts/quality/compare_renderer_pdfs.py` records page counts, page geometry, normalized
text, font/image resources, optional literal anchor rectangles and streamed raster comparisons.
Rasters use 96 DPI and channel tolerance 16. Pages are paired by ordinal, without reflow alignment.
Different page counts remain measurable failures rather than aborting the comparison.

Text equality can miss typography; extraction can reorder mathematical symbols. Resource counts
do not establish image fidelity. Changed-pixel fractions include white page area and are **not a
percentage of formatting correctness**. Zero observed raster change is bounded by DPI/tolerance;
the cross-platform hashes below additionally establish byte identity for those exact PDFs.
This audit does not certify arbitrary DOCX content or all STO clauses.

## Corpus and observed results

Four public controls cover both generator style presets; two existing private DOCX files exercise
larger reports without changing their original files or publishing their content. Private case IDs
C1 and R1 are intentionally anonymous. These existing artifacts are not claimed to have been rebuilt
from current Markdown. The public controls were freshly built from the current generator.

All six final Word acceptance receipts report accepted documents, stable saved/reopened page counts
and `processCleanupVerified: true`. The first C1 attempt selected the newer template against a legacy
DOCX and failed style validation after exporting its PDF; it is not counted as a successful acceptance.
The final run used the matching default preset. C1 and the 90-row table needed the launcher's bounded
interactive fallback after background timeouts. The Office license diagnostic warned, but the actual
final document operations passed.

## Concrete visual differences

Representative public pages were rendered side by side and inspected:

- Math, page 4: all control constructions are visible, but the fraction is smaller in Wordcraft;
  spacing, operator limits and the following paragraph's vertical position differ. Matching fonts
  do not remove this difference. Visibility is not a general proof of mathematical equivalence.
- Math TOC, page 3: both entries and target page numbers exist, but the entry block starts lower
  in Wordcraft and paragraph spacing differs.
- Long table, page 7: both repeat the column header and start with row 29. Word adds the continuation
  caption and fits through row 58; Wordcraft has no continuation caption and fits through row 59.
  The missing caption comes from the Word-only post-processing boundary, not missing source rows.

## Linux versus native Windows

The official native Windows x64 CLI was run on the example, math, long-table, C1 and R1 sources.
For all five, the resulting PDFs are **byte-identical** to Linux x86-64 under WSL with the controlled
font files. Independent page/text/raster comparisons also passed on all their pages, including C1's 66.
This demonstrates platform agreement for these builds and cases, while the Word comparisons still fail.
The second style-preset control was checked against Word on Linux; it was not separately run through
the Windows CLI.

No macOS host, standalone physical Linux host, ARM or RISC-V build was executed. Official asset
availability is recorded in the user matrix and must not be confused with platform acceptance.

## 0.8.0 versus 0.9.0

The three public live controls were also processed with the existing 0.8.0 CLI, using the same frozen
DOCX, controlled font set, statistic values and explicit field updates. Independent text and raster
comparison found no differences across their 24 paired pages at the stated DPI/tolerance.
The source controls therefore show no observed visual improvement from this release; they do not
exercise every upstream fix. No claim is made about speed or unrelated import formats.

Relevant upstream changes are linked in the compatibility matrix. `convert --update-fields` is new,
but our adapter already invokes `references.updateFields`; switching commands is unnecessary.
Upstream still documents pagination and mathematical-default limitations.

## Repeat the checks

Run the normal quality gate and the installed-engine controls:

```sh
npm run quality
npm run test:wordcraft
```

For a Word comparison, retain live outputs in a new managed scratch directory using
`WORDCRAFT_TEST_OUTPUT`, then run the required bounded launcher on each DOCX:

```sh
npm run accept:word -- /path/to/control.docx
python scripts/quality/compare_renderer_pdfs.py \
  /path/to/control.accepted.pdf /path/to/control.wordcraft.pdf \
  --anchor 'СОДЕРЖАНИЕ' --output /path/to/comparison.json
```

The comparison requires optional pypdf, pypdfium2 and Pillow in the chosen inspection runtime;
they are not generator dependencies. Exit 0 means only observed equality of the recorded checks,
1 means measured differences or unavailable raster inspection, and 2 means inspection/input failure.
It is not a Word acceptance replacement. Public live controls include a deliberately nonconforming
legacy style corpus, built raw for rendering tests rather than reported as source-preflight clean.
Never publish private comparison JSON containing extracted text differences.

Full temporary archives, DOCX/PDF copies, extracted binaries and logs are removed after evidence
capture. Compact hashes, measurements, acceptance receipts and selected public visual panels remain
as the audit evidence; original report files and the prior installed CLI are preserved.
