# Выпуски и версии

[GitHub Releases](https://github.com/Horcag/sto-report-generator/releases) содержит опубликованные
версии, архив CLI и автоматически собранные заметки по merged pull request.
Краткие изменения ведутся в [CHANGELOG](../CHANGELOG.md), планы — в [roadmap](../ROADMAP.md).

## Выбор версии

Используется стабильная схема `MAJOR.MINOR.PATCH`:

- `PATCH`: исправления с сохранением CLI, форматов конфигурации и поддерживаемого поведения.
- `MINOR`: новые возможности, команды или публичные материалы без нарушения совместимости.
- `MAJOR`: несовместимые изменения CLI, конфигурации или поддерживаемого формата отчётов.

Версия в `package.json`, обе корневые версии `package-lock.json`, заголовок `## X.Y.Z`
в CHANGELOG и тег `vX.Y.Z` должны совпадать. Автоматическая проверка намеренно допускает
только стабильные версии; предварительные выпуски потребуют отдельного изменения процесса.
Не следует менять опубликованный тег или повторно использовать номер версии.

## Подготовка выпуска

1. Соберите изменения в pull request, опишите поведение и результаты проверки.
   Для заметок используйте метки `breaking-change`, `enhancement` или `feature`, `bug` или `fix`,
   `documentation`, `maintenance`, `dependencies`, `ci`. Без метки PR попадёт в Other changes;
   `skip-changelog` исключает PR из автоматического списка.
2. Обновите пакет и lockfile командой `npm version X.Y.Z --no-git-tag-version`, добавьте
   раздел CHANGELOG и при необходимости обновите roadmap и примеры установки в README.
3. Выполните `node scripts/quality/check_release_version.cjs`,
   `node --test scripts/quality/tests/release_version.test.cjs`, проверку LF и `npm run quality`.
   Изменения формул и галереи также требуют соответствующих проверок и Word-приёмки.
4. После слияния PR и успешного CI создайте аннотированный тег на проверенном commit основной ветки:

    ```sh
    git tag -a vX.Y.Z -m "Release vX.Y.Z"
    git push origin vX.Y.Z
    ```

5. Дождитесь workflow Release. Проверьте опубликованную страницу, список PR, версию и наличие
   архива `sto-report-generator-X.Y.Z.tgz`. Обновлённый код, успешный CI и опубликованный релиз
   являются отдельными результатами.

## Что делает автоматизация

Push тега `v*` запускает проверку версии, тесты её валидации, проверку LF исходных байтов
в индексе и рабочей копии и полный `npm run quality`. Затем `npm pack` собирает архив,
который сохраняется как Actions artifact. Отдельный job с правом `contents: write` скачивает
этот архив и публикует GitHub Release через `gh release create --verify-tag --generate-notes`.
Категории заметок заданы в `.github/release.yml`; ссылка на CHANGELOG добавляется в описание.

Ручной `workflow_dispatch` выполняет проверки и сборку артефакта без публикации релиза,
в том числе при запуске на теге. Ошибка любого этапа блокирует следующий этап.
Если проверка завершилась ошибкой, исправьте причину до создания следующего тега.
Если сбой произошёл при публикации, сначала проверьте, не появился ли уже релиз: повторный
запуск не перезаписывает опубликованный выпуск автоматически.

Это публикация GitHub Release. Публикация в npm registry не настроена.
